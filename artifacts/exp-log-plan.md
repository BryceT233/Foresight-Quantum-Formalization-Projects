# Plan: `exp (log x) = x` for `‖x - 1‖ < 1`

**Status: proved.** `exp_log_one_add : exp (log (1 + x)) = 1 + x` for `‖x‖ < 1` and
`exp_log : exp (log y) = y` for `‖y - 1‖ < 1` are in `FQFP/BCH/Logarithm.lean` (public),
by the ODE route ported from `Lean-BCH/BCH/LogSeries.lean` — see §6. `lake build FQFP`,
`lake exe runLinter` and `lake exe lint-style` all pass. §1 is a mathematical correction that
matters if the route is ever restated; §§2–5 are the plan as it stood before the `Lean-BCH` file
was located.

## 1. The correction: there is no general-point formula `D log(y) = y⁻¹ •`

From `log y = ∑_{n≥1} cₙ (y - 1)ⁿ` with `cₙ = (-1)^{n+1}/n`, the derivative at `y = 1 + a` in the
direction `v` is, by the (noncommutative) product rule,

    D log(1 + a) · v = ∑_{n≥1} cₙ ∑_{k=0}^{n-1} aᵏ v a^{n-1-k}.

The linear part in `a` is `c₂(av + va) = -(1/2)(av + va)`, whereas left multiplication by
`y⁻¹ = (1+a)⁻¹ = 1 - a + O(a²)` gives `v - av`. So for noncommuting `a, v` the two differ, and

    D log(y) ≠ (v ↦ y⁻¹ * v)      (noncommutative `𝔸`).

This is not a defect of our definitions — the same phenomenon is visible upstream: in
`Mathlib/Analysis/SpecialFunctions/Exponential.lean`, `hasStrictFDerivAt_exp` (the statement
`D exp(x) = exp x • 1`) is documented as requiring **`𝔸` commutative** (module docstring, lines
29–31 and 43–45). The noncommutative version is only available *along the special curve*
`u ↦ exp (u • x)` with an intermediate **commutative** algebra `𝕊`
(`hasFDerivAt_exp_smul_const`, line 347). `D exp(X) · V = exp(X) * V` is false in general; the true
formula is `∫₀¹ e^{sX} V e^{(1-s)X} ds`.

**What survives, and what the ODE route actually needs.** If `v` *commutes* with `a`, then
`∑_{k=0}^{n-1} aᵏ v a^{n-1-k} = n a^{n-1} v`, so

    D log(1 + a) · v = ∑ₙ cₙ n a^{n-1} v = ∑ₙ (-1)^{n+1} a^{n-1} v
                     = (∑_{m≥0} (-1)^m a^m) v = (1 + a)⁻¹ v        (for `‖a‖ < 1`).

Along the curve `t ↦ log (1 + t • x)` the direction is `x` and the base point is `a = t • x`, which
*does* commute with `x` (both are in the commutative subalgebra generated by `x`). Hence

    d/dt log (1 + t • x) = (1 + t • x)⁻¹ * x        (the plan note's formula — correct as a curve)

and the same commuting-direction collapse applies to the `exp` step: the direction
`-(1 + t • x)⁻¹ * x` commutes with `log (1 + t • x)`, so `D exp` acts as multiplication by `exp`.

**Consequences for the plan.**
- Target the two **curve** derivatives, not general-point `fderiv`s.
- Do **not** state `fderiv ℝ log y = (mulLeft y⁻¹)` anywhere; it is false as a general statement.
- The general-point `fderiv ℝ log y` is *available* in the form
  `continuousMultilinearCurryFin1 ℝ 𝔸 𝔸 ((logSeries ℝ 𝔸).changeOrigin (y - 1) 1)` (see §3), which is
  correct but useless for the ODE unless specialised to a commuting direction.

## 2. Exact targets

For `𝔸` a complete normed `ℝ`-algebra (`[NormedRing 𝔸] [NormedAlgebra ℚ 𝔸] [NormedAlgebra ℝ 𝔸]
[CompleteSpace 𝔸]`), and `x : 𝔸`:

1. `h_log : ∀ t : ℝ, ‖t • x‖ < 1 → HasDerivAt (fun s : ℝ => log (1 + s • x)) ((1 + t • x)⁻¹ * x) t`
2. `h_exp : ∀ t : ℝ, ‖t • x‖ < 1 → HasDerivAt (fun s : ℝ => exp (-(log (1 + s • x))))
     (exp (-(log (1 + t • x))) * (-((1 + t • x)⁻¹ * x))) t`
3. `h_prod : ∀ t, HasDerivAt (fun s => exp (-(log (1 + s • x))) * (1 + s • x)) 0 t`
   — from 1, 2 and the product rule, because `(1+t•x)⁻¹ * x * (1+t•x) = x`
   (which is `a * (1+a) = (1+a) * a`, i.e. trivially true — no commutativity needed here).
4. `t ↦ exp (-(log (1 + t • x))) * (1 + t • x)` is constant, by
   `(∀ t, HasDerivAt F 0 t) → F constant` on `ℝ` (interval/convex argument); evaluate at `t = 0`
   using `log_one` (`log 1 = 0`), giving `exp (-(log (1+x))) * (1 + x) = 1`.
5. From 4, `exp (log (1 + x)) = 1 + x` for `‖x‖ < 1`, via `exp_neg`/`exp_add_of_commute` (the two
   factors commute) and uniqueness of the inverse; then restate for `‖y - 1‖ < 1` as
   `exp (log y) = y`.

## 4. Proof strategy for the missing brick: `h_log`

This is the only piece with no ready-made Mathlib lemma. Two routes.

**Route A (power series, in the manifest — recommended).** `hasFPowerSeriesOnBall_log_one_add_real`
gives `HasFPowerSeriesOnBall (fun y => log (1 + y)) (logSeries ℝ 𝔸) 0 1`. Then
`HasFPowerSeriesOnBall.fderiv_eq` at the interior point `a = t • x` gives

    fderiv ℝ (fun y => log (1 + y)) a = continuousMultilinearCurryFin1 ℝ 𝔸 𝔸 ((logSeries ℝ 𝔸).changeOrigin a 1).

Evaluating at `x` (the chain rule with `s ↦ s • x`, or directly) reduces the closed form to

    ∑_{l≥0} c_{1+l} ∑_{j=0}^{l} a^j x a^{l-j},

and since `x` commutes with `a` this is `∑_{l≥0} c_{1+l} (l+1) a^l x = (∑_{m≥0} (-1)^m a^m) x =
(1 + a)⁻¹ x`, the last step being the geometric series from `hasFPowerSeriesOnBall_inverse_one_add`.
The bookkeeping is the `changeOrigin` coefficient computation (`changeOriginSeriesTerm_apply`,
`le_changeOriginSeries_radius`, `changeOrigin_eval`); no new mathematics, but a real amount of
`Finset`/`tsum` manipulation.

**Superseded by §6.** The verified `Lean-BCH` file computes the same derivative **without** touching
`changeOrigin` at all, by term-by-term differentiation of the `tsum` with
`hasDerivAt_tsum_of_isPreconnected`. That route is simpler and is the one to port; the
`changeOrigin` route above is kept only as the alternative if the `tsum` route hits a wall.

**Route B (formal power series, possibly cheaper for the final theorem only).** `expSeries` and
`logSeries` are both `ofScalars`, so in the composition `expSeries.comp logSeries` every term over a
tuple `(v₁, …, vₙ)` is `c · (v₁⋯vₙ)` with the *same* ordered product (the `changeOrigin`/composition
bookkeeping multiplies `ofScalars` terms, which are scalar multiples of `∏ xᵢ`). So the multilinear
composition coefficients are the *one-variable* coefficients of `exp (log (1 + T))` in `A⟦T⟧`. On
paper: for `n = 3` the composition sum is `(1/3)vwu + (1/2)[-(1/2)vwu - (1/2)vwu] + (1/6)vwu = 0`
and in general `(expSeries.comp logSeries) n = δ_{n,1} · (product)`, i.e. `expSeries.comp logSeries`
is the series of `1 + X`. If `PowerSeries` has (or can cheaply get) the identity
`exp (log (1 + X)) = 1 + X`, Route B gives `exp (log (1 + x)) = 1 + x` directly through
`HasFPowerSeriesAt.comp` plus uniqueness of power series — **no derivatives, no ODE, no
`HasSummableGeomSeries`**. It does not give the derivative facts, so it is a shortcut to
`exp_log`, not to the ODE spine.

Recommendation: start with Route A's closed-form computation (it is the ODE spine and the user's
chosen route), and keep Route B in reserve — if `A⟦T⟧`'s `exp_log` identity exists, it is likely the
cheapest path to `exp_log` itself.

### 6.1 The three APIs that close the gap

| their lemma | what it provides | Mathlib tool behind it |
|---|---|---|
| `hasDerivAt_logOnePlus_smul` (line 676) | `d/dt log(1+t•x)` for all `t` in `|t|‖x‖ < 1`, as the tsum `∑' n, ((-1)^n t^n) • x^(n+1)` | **`hasDerivAt_tsum_of_isPreconnected`** (`Analysis/Calculus/SmoothSeries.lean:89`) — term-by-term differentiation of a `tsum` on an interval, with a dominating summable series and a uniform bound on the derivatives |
| `hcancel` inside `exp_logOnePlus` (lines 826–831) | `(∑' n, (-(t•x))^n) * (1 + t•x) = x` | **`geom_series_mul_neg`** (`Analysis/SpecificLimits/Normed.lean:312`): `(∑' i, x^i) * (1 - x) = 1` |
| `hasDerivAt_exp_of_hasDerivAt_commute` (line 706) | the chain rule for `exp ∘ f` when the increment commutes with `f t` | `exp (f s) = exp (f t) * exp (f s - f t)` (`exp_add_of_commute`) + **`hasFDerivAt_exp_zero`** (exp's derivative *at `0`*, which needs no commutativity) + `HasFDerivAt.comp_hasDerivAt_of_eq` |

The third one is the answer to the obstacle in §1: the general `D exp(X)` is never needed. Writing
`exp (f s) = exp (f t) * exp (f s - f t)` reduces everything to the derivative of `exp` at `0` (which
is `1`) multiplied by the derivative of the inner curve. This is where the commutativity hypothesis
`∀ s, Commute (f t) (f s - f t)` enters, and it holds because all of `log (1 + s • x)` lies in the
commutative subalgebra generated by `x` (their `commute_logOnePlus_smul`, line 698 — in our file
this is `Commute.log` applied twice).

### 6.2 What has to change for the current setting

Their file is built on `logOnePlus x = ∑' n, logSeriesTerm x n` with
`logSeriesTerm x n = (-1)^n/(n+1) • x^(n+1)`, over an `RCLike 𝕂`, with the scalar field threaded
through `include 𝕂` / `omit` and an explicit `NormedAlgebra.restrictScalars ℝ 𝕂 𝔸`. In the current
file:

- the function is `log`, defined through `FormalMultilinearSeries`, and `log_eq_tsum ℝ` already
  states it as a `tsum` over `ℝ`;
- **no reindexing is needed.** Their `logSeriesTerm` index `n ↦ x^(n+1)` is a shift of our
  `n ↦ x^n`, and their proofs are written against the shifted index. It turns out the unshifted
  index is fine: `log_eq_tsum` already carries it, the `n = 0` term vanishes automatically (its
  coefficient is `(-1)/0 = 0`), and term-by-term differentiation of `∑' n, ((-1)^(n+1)/n) • (s•x)^n`
  gives `∑' n, ((-1)^(n+1) • s^(n-1)) • x^n` whose `n = 0` term is again `0`. The interface lemma
  `log_one_add_smul_eq_tsum` is therefore a **one-liner** and is already landed in `Logarithm.lean`:
  ```lean
  private lemma log_one_add_smul_eq_tsum (x : 𝔸) (s : ℝ) :
      log (1 + s • x) = ∑' n : ℕ, (((-1 : ℝ) ^ (n + 1) / n) • (s • x) ^ n) := by
    rw [congrFun (log_eq_tsum ℝ) (1 + s • x), add_sub_cancel_left]
  ```
- their scalar-independence lemmas `logSeriesTerm_eq_real` / `logOnePlus_eq_real` (and the whole
  `RCLike 𝕂` + `restrictScalars` apparatus) are **superseded** by the ℝ layer already in this file
  (`logSeries_radius_eq_one_real`, `hasFPowerSeriesOnBall_log_one_add_real`, and `log_eq_tsum ℝ`).
  Nothing of that apparatus needs porting.
- their norm estimates (`norm_logSeriesCoeff_le`, `norm_logSeriesTerm_le`,
  `summable_logSeriesTerm`, `norm_logOnePlus_le`, and the whole stack
  `norm_logOnePlus_sub_…_le` up to order 8, lines 90–490) are **not** needed for `exp_log`; they are
  the BCH error-bound material and can be ported later if the project wants them.
- their `exp_logOnePlus_real` / `exp_logOnePlus_complex` (lines 521, 567), which compare with
  `Real.exp`/`Complex.exp`, are outside the current scope.
